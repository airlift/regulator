## Is Regulator native code?

No. Regulator is pure Java: there is no JNI library and no bundled native
code. With `--enable-native-access=ALL-UNNAMED`, eligible DFA searches keep
their transition table in native memory allocated through the JDK's foreign
memory API. That memory is storage, not code, and the API never exposes
native pointers. See
[Should I enable the Vector API or native access?](#should-i-enable-the-vector-api-or-native-access).

## How can a Java engine beat the Rust regex crate?

On many workloads it does, and on some it does not. The
[README summary](../README.md#performance), measured on Graviton with native
access enabled and patterns reused, puts Regulator ahead of the crate on
everyday expressions and behind it on text processing. The
[benchmark report](https://airlift.github.io/regulator/benchmarks/) has every
row, both platforms, and pure-Java results.

The short version: fast scans and cheap checks keep most input bytes away from
any automaton, compilation picks a specialized route for each pattern's shape,
and the JIT compiles the routes in use with the running workload's profile.
[Why Regulator is fast](WHY_FAST.md) explains the mechanisms and where the
crate still wins.

## Regulator is an RE2 port. Why is it faster than RE2?

The matching algorithms and their linear-time and bounded-memory guarantees
are ported from RE2. Most of the speed comes from work added on top: fast
early rejection, literal and multi-literal scans, vector and word-at-a-time
kernels, a DFA table and loops tuned for the JVM, extended OnePass and
BitState capture engines, and specialized plans for common shapes such as
URL or key-value extraction. [Why Regulator is fast](WHY_FAST.md) walks
through them; the [optimization catalog](reference/OPTIMIZATION_CATALOG.md)
lists each one.

## Where do the optimizations come from?

Some are ported from RE2, some from the Rust `regex` crate,
`regex-automata`, and `aho-corasick`, a few from Trino, and many were
developed here. The [optimization catalog](reference/OPTIMIZATION_CATALOG.md)
credits each one's source, and marks an origin unknown when the history does
not record one. The [RE2 optimization registry](reference/OPTIMIZATION_REGISTRY.md)
details the C++ RE2 optimizations. The license notices for ported code are in
[LICENSE-re2.txt](../LICENSE-re2.txt) and
[LICENSE-rust-regex.txt](../LICENSE-rust-regex.txt).

## Do optimizations ever change results?

No. Every specialized route must produce exactly what the ordinary engine
produces under the pattern's language. For RE2, Java, Rust, and SQL `LIKE`
patterns this holds on any input, malformed UTF-8 included. For Trino regular
expressions it holds on valid UTF-8, and malformed input is garbage in,
garbage out. Each language follows its own authority, listed in
[Language Authorities](../REGULATOR_DECISIONS.md#language-authorities), and
the [test map](porting/TEST_MAP.md) names each language's test oracle. The
[maintenance guide](MAINTAINING_REGULATOR.md) defines the correctness gates a
change must pass.

## Does matching run in linear time?

Yes. The shared engine runs each search in time linear in the input, with
bounded memory, so it avoids the catastrophic cases of backtracking engines.
Operations over every match, such as `count`, find loops, and replace, repeat
the search from each match end, or one character past an empty match, so their
total can be quadratic when each search reads far past its match, as `a+b|a`
does over a long run of `a`. RE2 and the Rust crate behave the same way.
Specialized routes also keep each individual search linear, and a scan plan
hands the rest of a search to the ordinary engine once its failed attempts in
that search exceed a work budget. The price is that features which need
backtracking are not supported. See the
[execution contract](reference/languages/UNSUPPORTED_FEATURES.md#current-execution-contract).

## How much memory does a pattern use?

Each compiled regular expression has a planning budget, 96 MiB by default,
that covers compilation and the lazily built DFA caches; each capture search in
progress may also hold working memory beside it, and a `RegexpMatcher` keeps
that memory for later finds (see
[Compiled patterns](reference/REGULATOR_API.md#compiled-patterns)). SQL `LIKE`
patterns have no budget. Simple patterns retain only what they use.
Compilation that exceeds the budget throws
`RegexpCompileMemoryLimitException`. During matching, a full DFA cache resets,
and repeated resets fall back to the NFA, so ordinary matching never throws a
memory-limit exception. `Re2Set` is the exception: it throws
`RegexpMatchMemoryLimitException` rather than report no match. The budget is a
planning budget, not an exact heap limit, and it excludes caller input, result
objects, and output. See [Compiled patterns](reference/REGULATOR_API.md#compiled-patterns)
and [Memory Budgets And DFA Caching](../REGULATOR_DECISIONS.md#memory-budgets-and-dfa-caching).

## Which features are not supported?

Java and Trino patterns reject backreferences, lookaround, atomic groups and
possessive quantifiers, `\G`, and surrogate escapes (Java accepts an escaped
surrogate pair). Trino also rejects non-ASCII byte escapes. Java also rejects
`\R`, grapheme clusters, nullable repeated captures, and canonical
equivalence. All four regular-expression languages reject repetition counts
above 1,000. Most of these conflict with linear-time matching or need
substantial compatibility work. The Java and Trino compilers name the feature
in the error. RE2 and Rust reject backreferences, lookaround, and the other
backtracking constructs as invalid syntax, as their upstreams do. Rust's
1,000 repetition limit is Regulator's own, and its error names the limit.
RE2's `\C` and Rust byte mode's byte escapes are supported. See
[Unsupported features](reference/languages/UNSUPPORTED_FEATURES.md).

## Is it thread-safe?

Compiled patterns are immutable and safe to share across threads; they do not
need to be closed. Matchers such as `RegexpMatcher` hold mutable state and
reusable workspaces, so give each thread its own. Lazily built DFA caches
belong to the compiled pattern; searches read them without a lock. See
[Compiled patterns](reference/REGULATOR_API.md#compiled-patterns) and
[Shared DFA Concurrency](../REGULATOR_DECISIONS.md#shared-dfa-concurrency).

## Should I enable the Vector API or native access?

Both are optional and change only execution strategy, never syntax, results,
captures, or failure behavior. They can be enabled independently.

- The Vector API speeds up candidate scans on long searches. It is used when
  the JVM's preferred byte vector holds 16 to 64 bytes; otherwise the scalar or
  word-at-a-time scanners run.
- Native access mainly helps DFA-heavy operations. Its effect depends on the
  pattern, input, and engine, and SQL `LIKE` routes do not use the DFA.

Start with the pure-Java default, and when regex execution is a substantial
part of your workload's cost, measure it with and without each flag. The
[benchmark report](https://airlift.github.io/regulator/benchmarks/) shows
native-access and pure-Java results side by side. See
[Runtime acceleration](reference/REGULATOR_API.md#runtime-acceleration).

## When should I use generated bytecode?

When a pattern is compiled once and applied many times from a call site that
holds it as a constant, such as a query engine that generates code per query.
The option is off by default and never changes results. An eligible pattern
gets its own hidden JVM class; a caller that binds the pattern's method as a
constant lets the JIT inline that class's code. The README puts generated
patterns at typically about 1.5–2× faster than the default compiled form. A
matcher's iteration does not get that benefit, because the matcher reaches the
pattern through an ordinary field. See
[Generated bytecode](reference/REGULATOR_API.md#generated-bytecode) and
[Binding a compiled pattern](reference/REGULATOR_API.md#binding-a-compiled-pattern).

## How are the benchmark results measured?

On AWS R9g (Graviton) and R8i (Intel) hosts, never on laptops. Each comparison
runs corresponding public operations in each library with its own input and
output types, and input conversion is outside the timings. JVM timings use JMH
with independent forks; native RE2 and the Rust crate run through a C++
harness. Results are averaged across at least three independent hosts and
reported with approximate 95% intervals. A difference whose interval includes
parity, or one too small to matter, is shown as a tie; the report also labels
the first "no clear difference". The README summary is a geometric mean of
per-workload time ratios, which describes the benchmark collection, not any
application's workload mix. See
[Benchmark methodology](benchmarks/METHODOLOGY.md),
[Workload organization](benchmarks/WORKLOAD_ORGANIZATION.md), and
[Measurement quality](benchmarks/MEASUREMENT_QUALITY.md).
