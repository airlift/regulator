## Is Regulator native code?

No. Regulator is pure Java: there is no JNI library and no bundled native
code. With `--enable-native-access=ALL-UNNAMED`, eligible DFA searches keep
their pointer table of transitions in native memory, allocated through the
JDK's foreign memory API, instead of a Java array. That memory is storage, not
code, and the API never exposes native pointers. See
[Should I enable the Vector API or native access?](#should-i-enable-the-vector-api-or-native-access).

## How can a Java engine beat the Rust regex crate?

The question assumes that Java is inherently slow, and that premise is wrong.
The JVM's JIT compiler profiles the running code and generates machine code
for the paths the program actually uses, so an engine's hot loops run as
machine code.

On many workloads Regulator does beat the crate, and on some it does not. The
[README summary](../README.md#performance), measured on Graviton with native
access enabled and patterns reused, puts Regulator ahead of the crate on
everyday expressions and behind it on text processing. The
[benchmark report](https://airlift.github.io/regulator/benchmarks/) has every
row, both platforms, and pure-Java results.

Regulator implements an equivalent of each search strategy the `regex` crate
uses by default (its literal prefilters, the reverse anchored, suffix, and
inner strategies, the lazy DFA, the one-pass DFA, the backtracker, and the
PikeVM), though some with different kernels. It adds many the crate lacks,
though few began in Regulator: DFA steps that advance two bytes per load,
first described for hardware DFAs; vector scans over self-looping lazy DFA
states, adapted from Hyperscan's DFA acceleration and acceleration in the
crate's fully compiled DFA; and scan plans for common pattern shapes, adapted
from ClickHouse. Regulator has no fully compiled DFA; the crate leaves its
fully compiled DFA off by default. The JIT then specializes those routes: a
call site that uses one pattern sees one implementation, and vector scans
compile to the running CPU's vector instructions. The Rust crate could likely
catch up if it added the same optimizations.

The short version: fast scans and cheap checks keep most input bytes away from
any automaton, compilation picks a specialized route for each pattern's shape,
and the JIT compiles the routes in use with the running workload's profile.
[Why Regulator is fast](WHY_FAST.md) explains the mechanisms and where the
crate still wins.

## Regulator is an RE2 port. Why is it faster than RE2?

The matching algorithms and their linear-time and bounded-memory guarantees
are ported from RE2. Most of the speed comes from work added on top, much of
it drawn from other engines: fast early rejection, literal and multi-literal
scans, vector and word-at-a-time kernels, a DFA table and loops tuned for the
JVM, extended OnePass and BitState capture engines, and specialized plans for
common shapes such as URL or key-value extraction.
[Why Regulator is fast](WHY_FAST.md) walks through them; the
[optimization catalog](reference/OPTIMIZATION_CATALOG.md) lists the main ones
and credits their sources.

## Where do the optimizations come from?

Few began here. The matching engines are ported from RE2, and most of the
optimizations were first built in RE2, the Rust `regex` crate and its `memchr`
and `aho-corasick` crates, Hyperscan, ClickHouse, .NET, Trino, and the
string-matching literature. Regulator's own work is mostly making them work
together across four regex languages and fast on the JVM. The
[optimization catalog](reference/OPTIMIZATION_CATALOG.md) credits the sources
of each optimization it lists and says whether it was ported, adapted, first
described elsewhere, or inspired by another engine; a part of an entry
credited to Regulator means a search found no earlier source. The
[RE2 optimization registry](reference/OPTIMIZATION_REGISTRY.md) details the
C++ RE2 optimizations. The license notices for ported code are in
[LICENSE-re2.txt](../LICENSE-re2.txt) and
[LICENSE-rust-regex.txt](../LICENSE-rust-regex.txt).

## Do optimizations ever change results?

No. Every specialized route must produce exactly what the ordinary engine
produces under the pattern's language. For RE2, Java, Rust, and SQL `LIKE`
patterns this holds on any input, malformed UTF-8 included. For Trino regular
expressions it holds on valid UTF-8, and malformed input is garbage in,
garbage out. Each language follows its own authority, listed in
[Language Authorities](../REGULATOR_DECISIONS.md#language-authorities), and
the [test map](porting/TEST_MAP.md) names each language's test oracle. The
[maintenance guide](MAINTAINING_REGULATOR.md) defines the correctness gates a
change must pass.

## Does matching run in linear time?

Yes, per search. Every search, including specialized routes, runs in time
linear in its input with bounded memory, so it avoids the catastrophic cases
of backtracking engines. Operations over every match, such as `count`,
repeated `find` calls, and replacement, can total quadratic time, as in RE2
and the Rust crate. The price is that features which need backtracking are
not supported. See the
[execution contract](reference/languages/UNSUPPORTED_FEATURES.md#current-execution-contract).

Compile-time hash tables mix
[MurmurHash3's fmix64](https://github.com/aappleby/smhasher/blob/61a0530f28277f2e850bfc39600ce61d02b518de/src/MurmurHash3.cpp#L81-L90)
with a per-process random seed, the defense
[Crosby and Wallach (2003)](https://www.usenix.org/legacy/events/sec03/tech/full_papers/crosby/crosby_html/index.html)
describe, so a crafted pattern cannot force hash collisions in every process.

## How much memory does a pattern use?

Each compiled regular expression has a planning budget, 32 MiB by default. It
covers the compiled program, its lazily built DFA caches, and the specialized
matchers that compilation plans for it. Parsing is not charged, and a compiled
pattern does not keep its parse tree. Each capture search in progress may also
hold working memory beside the budget, and a `RegexpMatcher` keeps that memory
for later finds (see
[Compiled patterns](reference/REGULATOR_API.md#compiled-patterns)). SQL `LIKE`
patterns have no budget. Simple patterns retain only what they use.

The default budgets of comparable engines:

| Engine | Default budget | What it covers |
|---|---|---|
| Regulator | 32 MiB per pattern | The program, every DFA cache, and planned matchers, two thirds for forward search and one third for reverse |
| RE2 | 8 MiB per pattern (`max_mem`) | The same, with the same split |
| Rust `regex` crate | 10 MiB per NFA (`size_limit`) and 2 MiB per lazy DFA cache (`dfa_size_limit`) | Each concurrent search holds its own caches, so the total grows with threads |
| JDK `java.util.regex` and Joni | None | Memory is bounded only by the heap and thread stack |
| PCRE2 | 20,000,000 KiB of match-time backtracking heap, plus match and depth limits | Backtracking during a match; no cache budget |

A Regulator pattern's DFA caches are shared by every thread inside its one
budget. Its default is 4 times RE2's because Regulator is built for data
processing, where one compiled pattern runs over many rows. The budget is a
cap, not a reservation: a typical benchmarked pattern settles at about 10 KB,
and the default keeps the large DFA graphs of nearly every benchmarked pattern
cached without resets. A pattern that needs more to compile, or to keep its
DFAs cached, takes a larger budget from `setMaxMemory`.

Compilation that exceeds the budget throws
`RegexpCompileMemoryLimitException`. Where compilation proves a lower bound on
the budget the pattern needs, the message reports it; a larger budget may still
be needed. During matching, a full DFA cache resets, and repeated resets fall
back to the NFA, so ordinary matching never throws a memory-limit exception.
`Re2Set` is the exception: it throws `RegexpMatchMemoryLimitException` rather
than report no match. The budget is a planning budget, not an exact heap
limit, and it excludes the pattern bytes, caller input, result objects, and
output. See [Compiled patterns](reference/REGULATOR_API.md#compiled-patterns) and
[Memory Budgets And DFA Caching](../REGULATOR_DECISIONS.md#memory-budgets-and-dfa-caching).

## Which features are not supported?

Java and Trino patterns reject backreferences, lookaround, atomic groups and
possessive quantifiers, `\G`, and surrogate escapes (Java accepts an escaped
surrogate pair). Trino also rejects non-ASCII byte escapes. Java also rejects
`\R`, grapheme clusters, nullable repeated captures, and canonical
equivalence. RE2, Java, and Trino patterns reject repetition counts above
1,000; Rust patterns take any count the crate does, bounded by the memory
budget. Most of these conflict with linear-time matching or need substantial
compatibility work. The Java and Trino compilers name the feature in the
error. RE2 and Rust reject backreferences, lookaround, and the other
backtracking constructs as invalid syntax, as their upstreams do. RE2's `\C`
and Rust byte mode's byte escapes are supported. See
[Unsupported features](reference/languages/UNSUPPORTED_FEATURES.md).

## Is it thread-safe?

Compiled patterns are immutable and safe to share across threads; they do not
need to be closed. Matchers such as `RegexpMatcher` hold mutable state and
reusable workspaces, so give each thread its own. Lazily built DFA caches
belong to the compiled pattern; searches read them without a lock. See
[Compiled patterns](reference/REGULATOR_API.md#compiled-patterns) and
[Shared DFA Concurrency](../REGULATOR_DECISIONS.md#shared-dfa-concurrency).

## Should I enable the Vector API or native access?

Yes, absolutely. Pass both flags to the JVM:

```text
--add-modules jdk.incubator.vector
--enable-native-access=ALL-UNNAMED
```

The Vector API is a large win. No benchmark switches it off for the whole
library, but where one route was measured both ways, moving inner-literal
search on inputs of 1 KiB or more from word-at-a-time code to vector code cut
its time to 0.50–0.60 of what it was on Graviton and 0.18–0.61 on Intel.

Native access is a smaller win, but not an insignificant one. Without it, the
DFA keeps the same pointer table in a Java array, which costs an addition per
step. On 14 DFA-heavy rows, most picked because native access had mattered
most there, the pure-Java table took about 5% longer than the native one at
the median on Graviton and 7% on Intel, and at most 15% longer on Graviton and
40% on Intel. On the same rows before pure-Java mode had that table, it took
about 35% longer at the median and up to 3.7 times as long. The published 2.0
preliminary report predates the Java-array table, so its overall
native-access gain does not describe the current implementation.

The [benchmark report](https://airlift.github.io/regulator/benchmarks/) runs
every row with and without native access, always with the Vector API on, so
its pure-Java results include vector scans.

Both flags are optional and can be enabled independently. They change only
execution strategy, never syntax, results, captures, or failure behavior.

- The Vector API speeds up candidate scans on long searches. It is used when
  the JVM's preferred byte vector holds 16 to 64 bytes; otherwise the scalar or
  word-at-a-time scanners run.
- Native access mainly helps DFA-heavy operations; SQL `LIKE` routes do not
  use the DFA.

See [Runtime acceleration](reference/REGULATOR_API.md#runtime-acceleration).

## How many uses does a pattern need to pay back its compile time?

Regulator spends more on compilation and planning than the JDK and Joni,
because it is built for data processing, where a pattern is compiled once and
run many times.

For patterns in the default compiled form, compilation alone takes tens of
times longer than the JDK's, and about 3 times longer than Joni's overall (1.3
to 9 times by pattern). It is close to native RE2's overall, though slower on
10 of the 13 everyday patterns, and faster than the Rust crate's on all but
one of them. The
[benchmark report](https://airlift.github.io/regulator/benchmarks/) estimates
how many uses Regulator needs to catch up with each comparator, from its
single-use and reused timings of everyday patterns; these are estimates, not
counted executions. With native access, Regulator catches up with the JDK
after about 90 uses at the median on both platforms (11 to 1,260 on Graviton).
It catches up with Joni after about 24 uses on Graviton and 29 on Intel.
Against native RE2 and the Rust crate, Regulator is ahead from the first use on
most everyday rows.

With [generated bytecode](#when-should-i-use-generated-bytecode), a pattern
compiles to its own JVM class, which costs more up front. Measured one fresh
pattern at a time on short synthetic rows, a generated pattern took about
1.3–2.1 ms to compile on Graviton (1.7–2.3 ms on Intel), against 0.01–0.14 ms
for the default form (0.02–0.22 ms on Intel). Its time per row leveled off
after roughly 0.26 to 1.0 million rows on Graviton (1.0 to 4.2 million on
Intel) while the JIT compiled the class. It overtook the default form after
about 0.6 to 1.2 million rows on Graviton (0.65 to 1.6 million on Intel), or
1.7 to 5.3 million on Graviton counting the JIT's own compile time. These
measurements predate a faster class generator, which barely moves the
break-even points, because the JIT's warm-up sets them.

## When should I use generated bytecode?

When a pattern is compiled once and applied many times from a call site that
holds it as a constant, such as a query engine that generates code per query.
The option is off by default and never changes results. An eligible pattern
gets its own hidden JVM class; a caller that binds the pattern's method as a
constant lets the JIT inline that class's code. The README puts generated
patterns at typically about 1.5–2× faster than the default compiled form, once
the JIT has compiled the class. A matcher's iteration does not get that
benefit, because the matcher reaches the pattern through an ordinary field. A
fresh generated pattern needs hundreds of thousands to millions of rows to pay
back its compile time and warm-up; the
[previous answer](#how-many-uses-does-a-pattern-need-to-pay-back-its-compile-time)
has the numbers. See
[Generated bytecode](reference/REGULATOR_API.md#generated-bytecode) and
[Binding a compiled pattern](reference/REGULATOR_API.md#binding-a-compiled-pattern).

## How are the benchmark results measured?

On AWS R9g (Graviton) and R8i (Intel) hosts. Each comparison runs
corresponding public operations in each library with its own input and output
types, and input conversion is outside the timings. JVM timings use JMH
with independent forks; native RE2 and the Rust crate run through a C++
harness. Results are averaged across at least three independent hosts and
reported with approximate 95% intervals. A difference whose interval includes
parity, or one too small to matter, is shown as a tie; the report also labels
the first "no clear difference". The README summary is a geometric mean of
per-workload time ratios, which describes the benchmark collection, not any
application's workload mix. See
[Benchmark methodology](benchmarks/METHODOLOGY.md),
[Workload organization](benchmarks/WORKLOAD_ORGANIZATION.md), and
[Measurement quality](benchmarks/MEASUREMENT_QUALITY.md).

You can run the benchmarks yourself, as
[AWS execution](benchmarks/METHODOLOGY.md#aws-execution) and the
[AWS collection guide](../tools/re2-benchmark/aws/README.md) describe, but one
full run on both platforms costs about $110 on AWS Spot.
